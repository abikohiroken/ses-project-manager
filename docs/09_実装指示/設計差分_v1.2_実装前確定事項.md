## 1. csv_imports の SKIPPED 制約矛盾【必須修正】

### 1.1 問題

`database_constraints.sql` の制約:

```sql
ADD CONSTRAINT "csv_imports_duplicate_state_ck"
CHECK (
  ("status" = 'SKIPPED' AND "duplicate_of_import_id" IS NOT NULL)
  OR
  ("status" <> 'SKIPPED' AND "duplicate_of_import_id" IS NULL)
);
```

これは「SKIPPEDなら必ず`duplicate_of_import_id`が入る」ことを強制する。

しかしCSV・Drive取込詳細設計 §17 のファイル結果判定では、

```text
success=0, failed=0, skipped>=1 → status=SKIPPED
```

すなわち「全行がDB既存案件で行スキップされた」場合もファイル全体をSKIPPEDとする。この場合ファイル自体は重複ではないため`duplicate_of_import_id`はNULLであり、**UPDATE時に必ず制約違反となり取込処理が落ちる。**

### 1.2 確定

SKIPPEDには性質の異なる2種類が存在することを明示し、制約を緩める。

| 種別 | 発生条件 | duplicate_of_import_id | error_code |
|---|---|---|---|
| ファイル重複 | file_hash一致の取込済みファイルが存在（取込設計 §12.6） | 元のcsv_imports.id | `FILE_DUPLICATE` |
| 全行スキップ | 全データ行がDB既存案件（取込設計 §17） | NULL | `ALL_ROWS_SKIPPED` |

制約を以下へ置き換える。

```sql
-- 置き換え後
ADD CONSTRAINT "csv_imports_duplicate_state_ck"
CHECK (
  "duplicate_of_import_id" IS NULL
  OR "status" = 'SKIPPED'
);
```

意味: `duplicate_of_import_id` を持てるのはSKIPPEDだけ。ただしSKIPPEDが必ず持つとは限らない。

### 1.3 error_code の用途拡張

`csv_imports.error_code` はエラー専用ではなく**終了理由コード**として扱う。SKIPPED時は上表の値を格納する。

スキーマ変更は不要（`error_code` は VarChar(64) NULL許容のまま）。

画面 SCR-006 では両者を区別して表示する。

## 2. csv_imports 作成タイミングの矛盾【必須修正】

### 2.1 問題

| 文書 | 手順 |
|---|---|
| 基本設計 v2.4 §11.3 | drive_file_idをINSERT → UNIQUE制約で処理権確保 → PROCESSING → ダウンロード |
| 取込詳細設計 §12 | ダウンロード → SHA-256 → 同一内容確認 → csv_imports作成（PROCESSING） |

先行INSERT方式では、この制約を満たせない。

```sql
ADD CONSTRAINT "csv_imports_downloaded_state_ck"
CHECK (
  "status" = 'ERROR'
  OR ("file_hash" IS NOT NULL AND "schema_version" IS NOT NULL AND "batch_id" IS NOT NULL)
);
```

INSERT時点ではまだダウンロードしておらず`file_hash`が算出できないため、PROCESSINGでのINSERTが制約違反になる。

### 2.2 確定

**取込詳細設計 §12 を正とする。** 基本設計 v2.4 §11.3 の手順2〜5は破棄する。

確定手順:

```text
1. ファイル名検証（正規表現）
2. サイズ検証（Driveメタデータ）
3. ダウンロード
4. SHA-256算出
5. 同一内容確認
6. csv_imports INSERT（status=PROCESSING、file_hash設定済み）
7. ヘッダー・行検証
8. 行登録
9. 結果判定・Drive移動
```

### 2.3 ERROR確定時のINSERT

ダウンロード前・ダウンロード失敗でERROR確定する場合は、`file_hash=NULL` のまま `status=ERROR` でINSERTする。これは `downloaded_state_ck` の `"status" = 'ERROR'` 分岐を満たす。

対象エラー: `INVALID_FILE_NAME` / `FILE_TOO_LARGE` / `DRIVE_DOWNLOAD_FAILED`

### 2.4 同時実行対策

先行INSERTをやめたことで、2プロセスが同一ファイルをダウンロードする窓が生じる。

確定:

- INSERT時の`drive_file_id`一意制約違反（Prisma P2002）は**「他プロセスが処理中」として当該ファイルをスキップ**し、次のファイルへ進む
- エラーとして記録しない。ログ（`event=file_already_claimed`）のみ
- ダウンロード帯域の重複は許容する（Schedule Jobは単一・30分間隔のため実質発生しない）

二重登録防止の最終的な担保は `csv_imports.drive_file_id` の一意制約であり、この方針でも維持される。

## 3. projects.project_code 採番規則【欠落補完】

### 3.1 問題

`project_code` は `@unique @db.VarChar(32)` かつ NOT NULL だが、生成規則がどの設計書にも定義されていない。正式案件登録APIが実装できない。

### 3.2 確定

形式:

```text
PRJ-YYYYMMDD-NNNN
```

| 要素 | 内容 |
|---|---|
| YYYYMMDD | 採番時点のJST日付 |
| NNNN | 当日連番。0001始まり、4桁ゼロ埋め |

例:

```text
PRJ-20260805-0001
```

### 3.3 採番手順

`POST /api/project-intakes/{id}/create-project` のSerializableトランザクション内で実行する。

```text
1. SELECT project_code FROM projects
     WHERE project_code LIKE 'PRJ-<JST日付>-%'
     ORDER BY project_code DESC LIMIT 1
2. 該当なし → 0001、あり → 末尾4桁 + 1
3. INSERT
```

- P2002（project_code重複）発生時は最大3回まで再採番リトライ
- 3回失敗で 500 `INTERNAL_ERROR`
- 当日9999件を超えた場合は 409 `PROJECT_CODE_EXHAUSTED`（初期規模では到達しない）

### 3.4 変更禁止

`project_code` は採番後に変更できない。API詳細設計 §7.3 の更新不可項目のまま維持する。

## 4. csv_imports.export_batch_id の一意制約衝突【必須修正】

### 4.1 問題

`export_batch_id` は `@unique` のため、同一`batch_id`に対して`csv_imports`が2件生じると2件目のリンクが失敗する。

同一内容CSVが別Driveファイルとして再配置された場合（取込詳細設計 §23.4 のテスト項目）に発生しうる。

### 4.2 確定

- `export_batches` へのupsertと `csv_imports.export_batch_id` の設定は、**status ∈ {SUCCESS, PARTIAL_SUCCESS} のときだけ**行う
- SKIPPED / ERROR の `csv_imports` は `export_batch_id = NULL` とする
- upsert対象の`export_batches`に既に別の`csv_imports`がリンク済みの場合は、リンクせず `export_batch_id = NULL` とし、`error_code = BATCH_ALREADY_IMPORTED` を記録する（処理自体は継続し、行登録結果は維持する）

取込詳細設計 §13.6 の「ファイル検証後にupsert」は、「**行登録完了後・結果判定時にupsert**」へ変更する。

## 5. merge API に統合先の楽観ロックを追加【API仕様変更】

### 5.1 問題

API詳細設計 §6.5 の `POST /api/project-intakes/{id}/merge` は、リクエストの`updatedAt`で**intakeの**競合しか検出しない。

しかし`applyFields`は既存`projects`レコードを更新する。統合先案件を別の利用者が同時編集していても検出できず、上書きが発生する。

### 5.2 確定

リクエストへ `targetProjectUpdatedAt` を必須追加する。

```json
{
  "updatedAt": "2026-08-05T15:00:00.000Z",
  "targetProjectId": "uuid",
  "targetProjectUpdatedAt": "2026-08-05T14:50:00.000Z",
  "applyFields": ["unitPriceMinMan", "startMonth"]
}
```

- `projects` の UPDATE の WHERE に `id` + `updated_at` + `project_status <> 'ARCHIVED'` を含める
- 更新件数0のとき:
  1. 対象なし → 404 `NOT_FOUND`
  2. ARCHIVED → 409 `INVALID_STATE_TRANSITION`
  3. updatedAt不一致 → 409 `OPTIMISTIC_LOCK_CONFLICT`（`details[].field = "targetProjectUpdatedAt"`）

### 5.3 画面への反映

画面詳細設計 §4.9 の統合モーダルは、案件検索結果から選択した案件の`updatedAt`を保持し、実行時に送信する。

`applyFields` が空配列の場合も、原文の関連付け（`project_sources.project_id`更新）とintakeのMERGED化は実行する。この場合`projects`はUPDATEしないが、`targetProjectUpdatedAt`の一致確認は行う。

## 6. 認証方式の確定【欠落補完】

### 6.1 問題

`schema.prisma` に Auth.js の `Account` / `Session` / `VerificationToken` モデルが存在しない。一方で画面詳細設計 §2.3 は「roleをJWTへ設定」と記述している。セッション戦略が未確定のまま実装すると、スキーマ変更が必要になり「migrationなしでDBを変更しない」に抵触する。

### 6.2 確定

| 項目 | 確定内容 |
|---|---|
| ライブラリ | Auth.js (NextAuth) v5、App Router対応版 |
| セッション戦略 | **JWT**（`session.strategy = "jwt"`） |
| Prisma Adapter | **使用しない** |
| Provider | Google のみ |
| スキーマ変更 | なし。`schema.prisma` v1.1 をそのまま使う |

### 6.3 サインイン制御

```text
1. Google OAuth成功
2. profile.email を trim + lowercase
3. users を email で検索
4. 該当なし → 拒否（画面: このアカウントは利用登録されていません）
5. is_active = false → 拒否（画面: このアカウントは無効です）
6. 許可 → users.last_login_at を更新
7. JWTへ users.id / role を格納
```

利用者の自動登録は行わない。ユーザーはADMINがSCR-007で事前登録する。

### 6.4 権限変更の即時反映

JWTはサーバー側で失効できないため、ロール変更・無効化が既存セッションへ即時反映されない。

確定:

- **更新系API（PATCH / POST）のRBACチェックは、JWTのroleではなく`users`テーブルを都度参照する**
- 参照系API・画面表示はJWTの値を使用してよい
- `is_active = false` のユーザーは更新系APIで 403 `FORBIDDEN` を返す
- JWT有効期間は8時間とする

この方式により、権限降格・アカウント無効化が更新操作に対して即時有効になる。

## 7. 環境変数の欠落補完【必須追加】

### 7.1 問題

全設計書の環境変数一覧に、**Auth.js の Google OAuth クライアント資格情報が存在しない**。

`GOOGLE_CLIENT_EMAIL` / `GOOGLE_PRIVATE_KEY` は Sheets/Drive API 用のサービスアカウントであり、利用者ログイン用のOAuthクライアントとは別物である。このままではログイン機能を実装できない。

### 7.2 確定

以下を追加する。

```env
# Auth.js Google OAuth（利用者ログイン用。サービスアカウントとは別）
AUTH_GOOGLE_ID=
AUTH_GOOGLE_SECRET=
AUTH_TRUST_HOST=true
```

- `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` は Auth.js v5 が自動認識する命名
- `AUTH_TRUST_HOST=true` は Dokployのリバースプロキシ配下でホスト判定を行うために必須
- 承認済みリダイレクトURI: `<APP_URL>/api/auth/callback/google`

### 7.3 秘密扱い区分

Application秘密（Dokployの秘密変数）へ追加:

```text
AUTH_GOOGLE_SECRET
```

## 12. Prisma 7 採用【2026-08-05 追記】

### 12.1 問題

`schema.prisma` は Prisma 6 形式で書かれている。Prisma の最新版は 7.9.1（2026-07-27）であり、Prisma 7 は `datasource` ブロックの `url` を受け付けない（P1012エラー）。

一方 Prisma 6 の最新は 6.19.3（2026-04-01、dist-tag `prev`）で保守モードに入っている。

### 12.2 検証結果

Prisma 7.9.1 に実際の `schema.prisma` を読ませて確認した。

| 項目 | 結果 |
|---|---|
| `url = env("DATABASE_URL")` | 拒否される。**削除が必須** |
| `generator provider = "prisma-client-js"` | **正常動作。変更不要** |
| `model` / `enum` / インデックス | **完全互換**。7テーブル / 7 enum / 34インデックスを設計どおり生成 |
| `PrismaClient` | ドライバアダプタ必須（`@prisma/adapter-pg`） |

### 12.3 確定

**Prisma 7（7.9.x系）を採用する。**

`schema.prisma` の変更許可は `datasource` ブロックの `url` 行の削除のみとする。データモデルは1バイトも変更しない。

理由:

- データモデルはPrisma 7で完全互換であることを実測で確認した
- コード0行の段階で保守モードのメジャー版に固定すると、将来の移行コストを確定させることになる
- Prisma 7 は Rust クエリエンジンを同梱しないため、Dockerのマルチステージビルドが単純化する

「`schema.prisma`を一文字も変更しない」という制約の目的は**DB設計v1.1で確定したデータモデルの保護**であり、接続設定のボイラープレートは対象外である。

### 12.4 実装への影響

詳細は `Phase1_実装指示書.md` §2.3 を参照。

- `prisma.config.ts` をリポジトリ直下へ新規作成する
- `PrismaClient` は `@prisma/adapter-pg` 経由で生成する
- `prisma generate` もビルド時に `DATABASE_URL` を要求する（Dockerのbuilder段階にダミー値が必要）
- `prisma migrate diff` のフラグ `--to-schema-datamodel` は `--to-schema` へ変更されている
